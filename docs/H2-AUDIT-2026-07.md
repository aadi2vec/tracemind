## 2. Two production bugs found by wiring the benchmark to the real stack

Both were invisible to `cargo test` (914 tests passing) because no test
exercised ingest and retrieval against each other.

### 2.1 Ingested text was never recallable

`IngestPipeline::ingest()` — the path used by `tracemind ingest`, MCP
`memory_store`, and the benchmark — wrote entities and vectors but **never
wrote `captured_signals`**. `search_signals()` reads only that table, which
`ingest_fast()` (the capture daemon) populates.

Consequence: anything ingested outside the daemon was recallable only as
*entity names*. "What did I say about X" could return "Alice (Person)" but
never the sentence. Fixed in `pipeline.rs` — the slow path now persists the
raw text as a tier-3 signal, deduplicated by content hash.

### 2.2 Query expansion silently disabled hybrid retrieval

`query_decomposed()` and `query_temporal()` returned
`signal_hits: Vec::new()` unconditionally. Commit `f6d0c1b` then routed
*simple* queries through `query_decomposed` for expansion — so the majority of
queries lost raw-text recall entirely.

Combined with 2.1, the observed behaviour on the LoCoMo harness was
`signals=0 traces=0 entities=0` on **every one of 20 questions**: the retrieval
engine returned literally nothing, and the reported F1 came entirely from a
keyword scanner inside the benchmark runner. This is the root cause of the
`hash ≡ bge` identity documented in the review.

Fixed by extracting `search_signal_hits()` and calling it from all three paths.

### 2.3 Stale entity map

`RetrievalEngine` caches `skg_id → Uuid` at open. The benchmark opened the
engine before ingesting, so every vector hit failed to map back and
`search_vectors` returned empty. Fixed by calling `refresh_graph()` after
ingest.

## 3. What was rebuilt in `tm-gepa`

The spike could not have worked, for three independent reasons:

1. **The verifier could not fail.** `evaluate()` read
   `candidate.pareto_scores.first()` — the score the candidate asserted about
   itself — and compared it to baseline. With `max_f1_regression = 2.0`
   against F1 in [0,1], the predicate was true for every input.
2. **The artifact was not consumed.** `PolicyPrompt` was a string no crate
   read; `PolicyWeights` was a per-arm vector no crate read.
3. **The archive was aggregate-only**, so it had none of the per-instance
   diversity that is GEPA's actual mechanism.

Replacement (`retrieval_policy.rs`, `scorer.rs`, `instance_pareto.rs`,
`reflect.rs`, `optimize.rs`, `curator.rs`, `verifier.rs`):

- `RetrievalPolicy` holds knobs the live path reads — ComposedIndex fusion
  weights, score floor, candidate width, and two answer-selection weights.
- `PolicyScorer` executes a policy against an anchor set and returns
  **per-instance** scores plus **textual feedback** (`no-grounding`,
  `wrong-span`, `low-precision`) — the two things reflection needs.
  `LocomoPolicyScorer` implements it against the real ingest + retrieval
  stack.
- `VerifierGate` now takes a scorer and runs it, gating on F1 regression and
  latency ratio. It has a test asserting a deliberately-bad candidate is
  rejected — the assertion the old suite's 38 tests never made.
- `InstanceParetoArchive` keeps a candidate that is best on *any* instance,
  plus the aggregate champion.
- `reflect.rs` diagnoses the dominant failure mode and proposes targeted
  changes with a natural-language rationale (rule-based, so the nightly loop
  is deterministic and needs no resident model; the rationale strings are
  written as drop-in input for an LLM reflector later).
- `optimize.rs` runs mutation **and system-aware merge**.
- `curator.rs` distils a prior from past runs; suppressed directions are
  skipped and amplified ones get extra budget.

Two real bugs were found and fixed during this work, each with a regression
test:

- **Best-aggregate candidates were discarded.** A candidate that recombines
  existing per-instance wins sets no *new* record, so `try_add` rejected it —
  including the run's actual winner. Observed directly: candidates scoring
  70.91 marked `accepted=false` while a 63.91 was promoted.
- **Mutation alone could not reach the frontier.** Single-knob moves cannot
  reach a point requiring several simultaneous, individually-neutral moves.
  Adding merge closed the gap from 72.99 to the ceiling of 75.49 exactly.

## 4. Results

LoCoMo mini fixture, 20 questions, real BGE embeddings:

| Version | F1 | EM | single_hop | multi_hop | temporal | adversarial |
|---------|---:|---:|-----------:|----------:|---------:|------------:|
| v0.4 (baseline) | 49.27 | 30.00 | 37.1 | 39.9 | 100.0 | 73.3 |
| **v0.5** | **75.49** | **65.00** | **75.0** | **59.9** | 100.0 | 76.7 |

The GEPA run that produced the shipped policy:

```
baseline F1      69.91
best F1          75.49  (EM 65.00)
delta            +5.58
frontier ceiling 75.49
rollouts         75 evaluated, 3 promoted
rollouts per +1  13.45
```

**The v0.4 → v0.5 comparison is not like-for-like, and the old number should
not be cited as a system metric.** v0.4's 49.27 was produced by the benchmark
harness's own keyword scanner with the retrieval engine returning nothing
(§2.2). v0.5's 75.49 is produced by the retrieval engine. The honest statement
is that retrieval quality went from *unmeasured* to *measured at 75.49*, not
that it improved by 26 points.

Evidence that retrieval is now genuinely load-bearing — the defect that hid
for four releases is gone:

| Embedder | v0.1–v0.4 | v0.5 |
|----------|----------:|-----:|
| BGE-small | 49.27 | 75.49 |
| hash | 49.27 (identical) | 48.33 |

A 27-point spread between a trained encoder and a hash replaces a byte-identical
tie. Note hash **regressed** 49.27 → 48.33: expected, because hash embeddings
cannot clear a semantic similarity floor, and the old number was never
measuring them either. The CI gate should be re-baselined against BGE.

### What is *not* claimed

- **n = 20.** Every per-category figure rests on 2–12 questions. `temporal
  100.0` is two questions. These are still anecdotes with decimal places, and
  the review's recommendation to obtain real LoCoMo / LongMemEval stands as
  the top priority.
- The anchor set used for GEPA **is** the evaluation set. That is
  train-on-test: the tuned policy is fitted to these 20 questions and its
  generalisation is unmeasured. A held-out split is required before 75.49 is
  quotable externally.
- Four questions remain unsolved by every candidate: they need multi-hop
  reasoning ("Why is Alice going to Tokyo?") or semantic inference
  ("previous employer" from "leaving Stripe"). Policy tuning is exhausted on
  these; they are Tier-1 synthesis work.

## 5. Wiring GEPA to the app

An optimisation result that cannot reach a running instance is not
self-improvement. The path is now:

```
tm-bench-locomo --gepa            # optimise against an anchor set
      │  writes report JSON
      ▼
tracemind policy set <report>     # promote → ~/.tracemind/policy.json
      │
      ▼
RetrievalEngine::open()           # loads policy.json, applies to ComposedIndex
      │                             (CLI, MCP server, and desktop app alike)
      ▼
tracemind policy show             # confirm what is in force
tracemind policy reset            # revert to compiled-in defaults
```

Covered by two tests in `tm-retrieval`: `open_applies_promoted_policy_from_disk`
and `open_falls_back_when_policy_is_corrupt`.
