# TraceMind — Honest Architecture & Product Review

**Date:** 2026-07-21
**Reviewed at:** `main` @ `11d57fe` + uncommitted Tier-1 candle work
**Scope:** architecture, benchmark validity, self-improvement design, product robustness

Everything below is reproduced from the repo as it stands today. Where I make a
claim I give the file, line, or command that backs it.

---

## 0. TL;DR

The engineering is real: 32 crates, 83k LOC, 914 tests, everything compiles and
runs locally with no cloud dependency. That part is not in question.

The problem is that **none of it is measured**. The headline number — F1 49.27 —
is produced by a 714-line hand-written string scanner running against a 20-question
fixture that the same author wrote, and the retrieval stack the product is built
around contributes *provably zero* to it. Meanwhile `tm-gepa`, the crate that is
supposed to make the system self-improving, has zero dependents and a verifier
that cannot fail.

The system optimizes what it can measure. It currently cannot measure anything
real. Everything else in this review is downstream of that one fact.

Priority order: **(1) build an honest eval, (2) close the reward loop on the
surface that actually ships, (3) then — and only then — turn on GEPA.**

## 1. The benchmark number does not mean what it says

### 1.1 Reproduced today

```
$ ./target/release/tm-bench-locomo --dataset .../locomo-mini.json --runner tracemind
tracemind-v0.1-hash  F1=49.27  EM=30.00  n=20  t=0.6s

$ ... --runner tracemind --real-embeddings
tracemind-v0.1-bge   F1=49.27  EM=30.00  n=20  t=4.5s
```

### 1.2 Finding: BGE and hash embeddings produce byte-identical results

Not "similar" — identical, per-question, at **every version v0.1 through v0.4**:

```
num outcome f1 diffs: 0
```

BGE-small-en-v1.5 is a 384-dim trained sentence encoder. `--hash-embed` is a
deterministic hash. They score the same to 15 decimal places on every question.

There is exactly one reading of this: **the embedding is not on the critical path
of the score.** The ONNX model, the fastembed integration, the auto-download, the
cosine index — none of it is being exercised by the number you report. You are
paying 7.5× latency (4.5s vs 0.6s) for zero measured gain.

### 1.3 Finding: the fixture is 5.9 KB and hand-written

`crates/tm-bench-locomo/fixtures/locomo-mini.json` is 5,950 characters. Three
conversations (Alice/Tokyo, Carol/fundraise, Ethan/marathon), 20 questions,
categories of size n=2 (temporal) and n=3 (multi-hop, adversarial).

The reported `temporal f1=100.0` is two questions. `adversarial f1=73.3` is three.
A single question flipping moves a category by 33 points. These are not
measurements; they are anecdotes with decimal places.

Real LoCoMo is ~50 conversations averaging 300 turns / 9k tokens across up to 35
sessions. The fixture is roughly **0.1%** of it and is structurally easier in every
dimension that makes LoCoMo hard: no long-range session drift, no distractor
entities, no genuinely unanswerable questions.

### 1.4 Finding: the v0.3 → v0.4 jump is largely one hardcoded prior

F1 went 25.70 → 49.27 in v0.4, attributed in `CLAUDE.md` to "Tier-0 span
extractors". Category deltas:

| category    | v0.3 | v0.4  | n |
|-------------|------|-------|---|
| adversarial | 25.1 | 73.3  | 3 |
| temporal    | 16.7 | 100.0 | 2 |
| single_hop  | 24.6 | 37.1  | 12|
| multi_hop   | 36.6 | 39.9  | 3 |

The adversarial and temporal gains come from `extract.rs`. Read its yes/no oracle
contract (`crates/tm-bench-locomo/src/extract.rs:311-322`):

> 5. If the turn has a typed value and the question doesn't → **"No, `<turn value>`"**
>    (the question's framing usually implies a contradiction)

That is an **assumed-contradiction prior**. Every adversarial question in the
fixture happens to be a contradiction, so the prior scores 73.3. It is not
answering the question; it is exploiting a property of three hand-written examples.

The failure it produces is visible in the baseline file:

```
multi_hop  f1=0.40 | Q: Did Ethan beat his goal?
     pred: 'No, Sub-3:00'
     ref : 'Yes'
```

Ethan ran 2:58:42 against a sub-3:00 goal. He beat it. The system says **No** —
and still collects 0.40 F1 from token overlap. Token-F1 is paying it for a wrong
answer. On real LoCoMo, where adversarial items are frequently *unanswerable* and
the correct behavior is abstention, this prior inverts from +48 to a systematic
error source.

Similarly, `classify_question` anchors on the literal strings `"finish time"`,
`"goal time"`, `"race time"`, `"split time"` (`extract.rs:63-70`) — which are the
exact phrasings of the fixture's questions. This is curve-fitting to the test set,
written as code.

### 1.5 What the real failure profile looks like

Stripping the extractor wins away, the 20 outcomes split into three groups:

**Retrieval genuinely failed (5/20, F1 ≈ 0)** — including two empty predictions:
```
Which airport did Alice fly into?  → "I'm flying to Tokyo on May 3rd..."  (Haneda is in s3)
What was Carol's previous employer? → ''                                   (Stripe)
Who led Carol's pre-seed round?     → 'Pre-seed, $1.5M target.'            (Sequoia)
How much did Carol raise?           → ''                                   ($2.5M)
What marathon did Ethan run?        → 'Did a 22-mile long run today...'    (Boston)
```

**Retrieval succeeded, the answer layer lost the points (5/20)** — right turn
retrieved, wrong span returned:
```
Where is Alice staying?      0.46  → whole turn instead of "Shinjuku"
What did Carol rename to?    0.20  → whole turn instead of "Memex"
Who is Carol's first hire?   0.25  → whole turn instead of "Priya"
Which training method?       0.36  → whole turn instead of "Hanson"
```

**Extractor won (5/20)** — dates, times, and the contradiction prior.

That second group is the honest good news: **~25% of the score is sitting there
waiting for a real synthesizer**, and it's exactly what the uncommitted Tier-1
candle work targets. That's the right instinct. But it should be measured on a
dataset that isn't the one the extractors were written against.

### 1.6 What to do

1. **Stop reporting 49.27 as a system metric.** It is a `tm-bench-locomo::extract`
   metric. Rename the artifact or add the caveat inline.
2. **Get the real LoCoMo-10 / LongMemEval-S.** `tm-bench-longmem` already exists
   (1,143 LOC) — wire it to real data. Any number on <200 questions has a
   confidence interval wider than every gain you've shipped.
3. **Make the CI gate two-sided.** Right now it fails on a >0.5 F1 drop. Add a
   gate that fails when `hash` and `bge` scores are within noise of each other —
   that condition means retrieval is disconnected, and it silently held for four
   consecutive releases.
4. **Add ablation runners** to `tm-bench-locomo`: `--ablate retrieval`,
   `--ablate extract`, `--ablate rerank`. If `--ablate retrieval` barely moves the
   score, you've learned that before you ship, not four versions later.
5. **Delete the phrase-anchored extractors** (`"finish time"` etc.) or move them
   behind a feature flag clearly marked as fixture-specific.

## 2. Architecture critique

### 2.1 The self-improvement machinery is not connected to anything

```
$ for c in crates/*/; do users=$(...); echo "$users <- $c"; done
0 <- tm-gepa
0 <- tm-engram
0 <- tm-modal
```

`tm-gepa` is 925 LOC with 38 passing tests and **zero consumers**. It is a
well-tested island. The same is true of `tm-engram` and `tm-modal`.

Worse, the parts that exist don't do what the names promise:

**The verifier gate cannot fail.** `crates/tm-gepa/src/verifier.rs:37-54`:

```rust
let candidate_f1 = candidate.pareto_scores.first().copied().unwrap_or(baseline_f1);
let regression = baseline_f1 - candidate_f1;
let passed = regression <= self.config.max_f1_regression;
```

It reads the score the candidate *claims about itself* and compares it to the
baseline. It never runs a query, never touches the retrieval engine, never
evaluates anything. With `max_f1_regression = 2.0` and F1 in [0,1], `passed` is
`true` for every possible input. The doc comment is honest about this — *"For the
spike, it uses synthetic scores"* — but the crate is described in `CLAUDE.md` and
the H2 charter as shipped.

**Prompt "mutation" is a sentence shuffle.** `crates/tm-gepa/src/policy.rs:65-77`:

```rust
pub fn paraphrase(&self) -> Self {
    // Simple deterministic paraphrase: reorder the sentences
    let mut s = sentences[1..].to_vec();
    s.push(sentences[0]);
    ...
}
```

Rotating sentence order is not reflective prompt evolution. GEPA's entire
contribution is that an LLM *reads execution traces including failures* and writes
natural-language lessons back into the prompt. Deterministic rotation has no
gradient — it will cycle through `n` permutations forever.

**The prompt it evolves is never used.** `PolicyPrompt::default_policy()` produces
a string ("Retrieve memories most relevant to the query…") that no crate consumes.
`RetrievalEngine::query()` is imperative Rust; there is no prompt in the retrieval
path for this to steer. You've built a prompt optimizer for a system with no prompt.

### 2.2 The reward signal is dead on the surface that ships

`crates/tm-retrieval/src/engine.rs:1690-1698`:

```rust
let relevance_reward = if pending.clicks > 0      { 0.7 }
                       else if rapid_requery      { 0.1 }
                       else if elapsed > 10s      { 0.5 }
                       else                       { 0.3 };
```

Now grep for who produces those signals:

```
crates/tm-tauri/src/main.rs:794:  engine.register_click(uuid);
crates/tm-tauri/src/main.rs:948:  engine.explicit_feedback(score);
```

**Only the Tauri desktop app.** `tm-mcp` — which the host-agnostic pivot made the
*primary* surface — never registers a click. There is no click in an MCP call.
There is no dwell. "Elapsed > 10s" measures how long the host model took to
generate its next tool call.

So on the shipping surface, the bandit receives a near-constant 0.3, occasionally
0.1 when the host issues two tool calls quickly. UCB1 and LinUCB are both learning
from a signal with no correlation to whether the memory was useful. `bandit.json`
and `linucb.json` are accumulating noise, being persisted, and being reloaded.

This is the single highest-leverage fix in the repo and it isn't a modeling
problem — it's a plumbing problem.

### 2.3 `RetrievalEngine::query()` is a 1,026-line method

`engine.rs:601` → `engine.rs:1627`. Inside it: planner classification, bandit
selection, vector search, signal hybrid, ColBERT rerank, RRA fusion, k-hop
expansion, MMR, episodic scan, reasoning chains, analogy solving, temporal
filtering, related-entity computation, confidence assessment, trace append, reward
registration.

Consequences that are already biting:
- You cannot unit-test a phase in isolation, which is why `tm-retrieval` has 21
  tests for 3,148 LOC (vs `tm-graph`'s 148 for 14,061).
- You cannot ablate a phase, which is why §1.2 went undetected for four releases.
- GEPA has nothing to optimize *over* — there is no declared pipeline, just
  control flow.

The `Space` trait and `ComposedIndex` (Q3.10) were the right idea. Finish the job:
`query()` should be a sequence of `Phase` objects with declared inputs, outputs,
and parameters. That single refactor is the precondition for §3 to be possible at
all.

### 2.4 Scale: two silent recall cliffs

`crates/tm-graph/src/store.rs:2549-2551`:

```rust
// For large backlogs, we could use ANN; for now linear scan is fine
let signals = self.unconsolidated_signals_by_tier(None, 2000)?;
```

Every query cosine-scores up to 2,000 signals in a Rust loop. Two problems:
- **Latency** grows linearly. Fine at 2k; at 100k captures from the daemon it isn't.
- **Silent truncation.** At >2,000 unconsolidated signals, the cap drops the tail
  with no error and no metric. Recall degrades quietly as a function of how long
  the user has had the product installed — the worst possible failure shape,
  because it looks like the product getting worse for no reason.

There is no ANN index anywhere (`grep -rn "hnsw\|Hnsw\|ANN"` → one comment). For a
local-first product this is fine *today* and a P1 before any real user has a month
of capture history.

### 2.5 Crate sprawl

32 crates / 83k LOC for a solo founder. Three have zero dependents. Several are
thin: `tm-engram` (350 LOC, 4 tests), `tm-bench-wme` (239 LOC, 0 tests),
`tm-bench` (1,047 LOC, 0 tests), `tm-modal` (548 LOC). Seven separate benchmark
crates, of which one is used.

Each crate is a `Cargo.toml`, a version bump, a CI target, and a place for
intent to hide. Recommendation: fold `tm-engram` and `tm-modal` into their
consumers-to-be or delete them; collapse `tm-bench*` into one crate with
subcommands. Keep `tm-gepa`, but rewrite it per §3.

### 2.6 What's genuinely good

Stated plainly so the critique is calibrated:

- **The trace log is the real asset.** Every ingest and query writes an immutable
  `Trace` with content hash and entity IDs. That is exactly the substrate GEPA
  needs and almost nobody building memory products has it. See §3.
- **914 tests** and a green workspace at this LOC is above average.
- **`tm-graph` is solid** — 148 tests, 14k LOC, the KG-R1 traversal is coherent.
- **The Tier 0/1/2 dispatcher shape is right.** Tier 0 always succeeding is the
  correct invariant for a local product.
- **The Tier-1 candle work in flight targets the right 25%** (§1.5, group 2).
- **Local-only is real**, not marketing — no network in the request path.

## 3. Self-improvement: what to actually build

The user's question was prompt / harness / stack optimization via GEPA. These are
three different problems and the current `tm-gepa` conflates them. Split them.

### 3.0 Precondition: GEPA needs three things you don't have

GEPA (Agrawal et al., 2025) is *reflective prompt evolution with Pareto-frontier
candidate selection*. It requires:

1. **A textual artifact to evolve** — a prompt or instruction string that actually
   steers behavior.
2. **A scorer that emits textual feedback**, not just a scalar. The reflection step
   reads *why* something failed. A float carries no gradient for an LLM.
3. **A task set with ground truth**, large enough that a delta is real.

TraceMind has (1) barely, (2) not at all, (3) not at all. Build them in that order.
Turning on the loop before then optimizes noise, and because the verifier is a
tautology, it will report success while doing it.

### 3.1 Layer A — Prompt evolution (this is where GEPA belongs)

**Evolvable artifacts that actually exist or should:**

| Artifact | Where | Status |
|---|---|---|
| Tier-1 synthesis prompt | `tm-answer/src/candle_backend.rs` | exists, hardcoded |
| MCP tool descriptions | `tm-mcp/src/main.rs` | exists, hand-written |
| Query-expansion instructions | `tm-retrieval` | hardcoded rules |
| Ingest-worthiness policy | `tm-ingest`, `is_relevant_for_ingestion` | hardcoded |
| Span-extraction rules | `tm-bench-locomo/src/extract.rs` | hardcoded, overfit |

**The highest-value target is the one you haven't considered: MCP tool
descriptions.** In the host-agnostic architecture, TraceMind's tool descriptions
*are* the prompt — they are the only text you control inside the host model's
context, and they determine whether Claude Code calls `memory_query` at the right
moment with the right phrasing. Right now they're hand-written and never measured.
This is "harness optimization" in the truest sense and it is a clean GEPA target:
short artifact, huge leverage, directly measurable as tool-call precision/recall.

**Loop shape:**

```
trace log (traces.jsonl)  ──▶  failure sampler
                                    │
                        ┌───────────┴────────────┐
                        │  reflection step       │   ← Tier-1/Tier-2 LLM reads
                        │  (LLM reads traces +   │     the trace AND the textual
                        │   textual feedback)    │     feedback, writes a lesson
                        └───────────┬────────────┘
                                    ▼
                          candidate artifact
                                    │
                        ┌───────────▼────────────┐
                        │  REAL verifier:        │   ← runs N anchor queries
                        │  execute anchor set    │     through the actual engine
                        └───────────┬────────────┘
                                    ▼
                    Pareto archive (per-instance scores)
                                    │
                            promote if no regression
```

**Non-negotiables when you rewrite `tm-gepa`:**

- `VerifierGate::evaluate` must take `&mut RetrievalEngine` (or a `Scorer` trait)
  and *execute* the anchor set. If it can't fail, it isn't a gate. Add a test that
  asserts a deliberately-bad candidate is rejected — the current suite has no such
  test, which is why the tautology survived 38 tests.
- The Pareto archive must hold **per-instance** scores, not aggregates. That's the
  whole mechanism — it's what preserves candidates that win on a minority of tasks
  and prevents collapse to a local optimum. `pareto.rs` currently keys on axes, not
  instances. Fix that.
- The scorer must return `(score, feedback: String)`. Feed the feedback to
  reflection. Without it you have a genetic algorithm, not GEPA.
- Run it nightly, offline, against a frozen anchor set. Never in the request path.

### 3.2 Layer B — Numeric/stack optimization (NOT GEPA)

Arm weights, fusion coefficients, `min_sim` thresholds, `top_k`, MMR λ, rerank α.
These are scalars. Applying `weight_perturb` mutation and calling it GEPA is a
category error — GEPA's power comes from *semantic* reflection, which has nothing
to say about `0.4 → 0.5`.

Use the right tool:
- **LinUCB already does this online.** It's the correct algorithm; it's just being
  fed a dead reward (§2.2). Fix the reward and this layer largely solves itself.
- For offline sweeps, use coordinate descent or CMA-ES over the frozen anchor set.
  ~50 lines, no LLM, deterministic, reproducible.
- Keep them in the **same Pareto archive** as Layer A so the promotion gate is
  unified — but with a different mutation operator.

### 3.3 Layer C — Close the reward loop (do this first)

This is the highest-ROI item in the entire review and it's mostly plumbing.

The MCP surface needs implicit signals that actually exist in an agentic context:

| Signal | Meaning | Source |
|---|---|---|
| Host cites returned memory in its next message | strong positive | parse host follow-up |
| Host immediately re-queries with a rephrasing | negative | `memory_query` within N s, high query similarity |
| Host calls `memory_store` right after a query | negative — it didn't find it, so it wrote it | tool-call adjacency |
| Session ends with no further memory calls | weak positive | session close |
| Explicit `memory_feedback` tool | ground truth | **new tool — add it** |

The last one is the cheapest and best: **add a `memory_feedback` MCP tool** and
describe it so the host model calls it. Hosts are cooperative — Claude Code will
call a well-described feedback tool. That turns a dead reward channel into real
supervision, at the cost of one tool definition.

Also: the `not-related` / `helpful` CLI commands already write
`negative_signals` / `positive_signals` rows and feed `finalize_pending_reward`.
The mechanism exists. It's just unreachable from MCP. Expose it.

### 3.4 Sequenced plan

| # | Item | Why | Effort |
|---|---|---|---|
| 1 | `memory_feedback` MCP tool + wire implicit signals | reward loop is dead on the shipping surface (§2.2) | S |
| 2 | Real LoCoMo/LongMemEval data + ablation runners | can't measure anything today (§1) | M |
| 3 | CI gate: fail when hash ≈ bge | this bug hid for 4 releases (§1.2) | S |
| 4 | Decompose `query()` into declared `Phase`s | precondition for everything below (§2.3) | L |
| 5 | Real `VerifierGate` executing anchor queries | current gate cannot fail (§2.1) | M |
| 6 | Per-instance Pareto archive | it's the actual GEPA mechanism (§3.1) | M |
| 7 | GEPA over MCP tool descriptions | highest-leverage prompt you control (§3.1) | M |
| 8 | GEPA over Tier-1 synthesis prompt | targets the measured 25% gap (§1.5) | M |
| 9 | CMA-ES / coord-descent for scalars | right tool for the numeric layer (§3.2) | S |
| 10 | ANN index for signals | silent recall cliff at 2k (§2.4) | M |

Items 1–3 are days and unblock honest measurement. Do not start 7–8 before 5.

## 4. Product robustness

### 4.1 The empty answer

Two of twenty predictions were `''`. In the product that is a memory query that
returns nothing, with no explanation. This is the worst failure shape available:
it's indistinguishable from "you never told me that", from "the daemon wasn't
running", and from "retrieval broke".

`RetrievalResult` already has `low_confidence: bool` and `suggested_queries`.
There is no `assess_confidence` function backing it (`grep` finds no definition),
so the flag is not calibrated against anything.

**Fix:** never return empty. Return one of three explicit states:
- `Found` — with citations to the source trace.
- `Uncertain` — "I have related context but not this: `<nearest neighbors>`."
- `NotStored` — "Nothing in memory covers this. Closest topics: X, Y."

For a memory product, a well-scoped "I don't know" is *more* trust-building than a
confident wrong answer. The current architecture (assumed-contradiction prior, §1.4)
is tuned in exactly the opposite direction — it manufactures confident answers
because token-F1 rewards them. That's a benchmark artifact leaking into product
behavior, and it will cost you user trust the first time it confidently inverts a
fact the user knows.

### 4.2 Nothing is evaluated on the surface that ships

Every benchmark measures the CLI/library path. Zero measure the MCP path. But the
product *is* the MCP server inside Claude Code. Unmeasured questions that decide
whether it's good:

- Does the host call `memory_query` when it should? (recall of the tool itself)
- Does it call it when it shouldn't? (precision — noise in the host's context)
- Is p95 tool latency inside the host's patience? BGE runs at 4.5s for 20 queries
  in-process; add model load and it's a different story on a cold call.
- What happens when `~/.tracemind/models/` is empty on first use and the download
  is slow or blocked? First-run is the highest-stakes moment and it depends on a
  network fetch in a product whose pitch is "local-only".

**Build `tm-bench-mcp`:** a scripted host transcript, replayed against the real
JSON-RPC server, scoring tool-call precision/recall and latency. That is the
product metric. It doesn't exist.

### 4.3 Cold start

Model auto-download on first use is a cliff: slow, network-dependent, and
contradicts the local-only promise at exactly the moment the user is forming an
opinion. Options, in order of preference: ship BGE + ColBERT in the installer;
otherwise download at install time with visible progress, and make Tier-0 fully
functional (it already is) with an explicit "running in reduced mode" state rather
than a silent stall.

### 4.4 Failure surfaces that need explicit handling

- **Capture daemon not running** → memory silently stops growing. Needs a
  liveness indicator surfaced in the MCP `memory_query` response.
- **>2,000 unconsolidated signals** → silent recall decay (§2.4). Needs a metric
  and a consolidation backpressure signal.
- **DB lock contention** — daemon writing while MCP reads, WAL mode helps but the
  behavior under contention is untested.
- **Corrupt / partial `traces.jsonl`** — it's the audit trail and the GEPA
  substrate. Needs a validate-and-repair path.

### 4.5 Trust surface

For a product whose entire pitch is privacy, two things should be first-class and
aren't clearly:
- A one-command **"show me everything you know about me"** export. `tracemind
  export` exists (LM-16) — make it the loudest thing in the README.
- A one-command **forget**, with proof: what was deleted, from which stores,
  including the trace log and the vector index.

## 5. The three things I'd change this week

1. **Add `memory_feedback` to MCP and wire implicit signals.** Your learning
   machinery is architecturally sound and receiving a constant. One tool
   definition turns four crates of dead code into a working loop. (§3.3)

2. **Get real LoCoMo data and add `--ablate`.** Until then, every number in this
   repo is a hypothesis. The hash≈bge finding took twenty minutes to surface and
   had been true for four releases. (§1.6)

3. **Make `VerifierGate` execute something, and write the test that a bad
   candidate is rejected.** A gate that cannot fail is worse than no gate, because
   it will report that self-improvement is working. (§2.1)

Everything else — GEPA over tool descriptions, phase decomposition, ANN — is
genuinely valuable and genuinely blocked on these three.
